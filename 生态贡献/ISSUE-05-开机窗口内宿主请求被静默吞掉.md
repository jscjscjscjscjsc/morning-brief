# ISSUE-05 · 开机头几秒内 `host.request` 被静默吞掉：无回执、无日志、无错误

**上报对象**：`makepad`（`widgets/src/splash_host.rs` 一侧的请求投递链路）+ 宿主侧调度
**严重度**：中高（**静默**：既没有回执也没有错误，调用方代码看起来"点了没反应"；
凡是"启动即探测"的应用都会被骗一次，且极难排查）
**状态**：未修；本仓库已按实测规律绕过（不在启动窗口发请求）

---

## 一句话

卡片启动后的大约 **0 ~ 4.5 秒**内发出的 `host.request(...)` **不会收到任何回执**
（callback 不跑、无报错、宿主日志无记录），约 4.5 ~ 12 秒之间时通时不通，
12 秒以后稳定可靠。用户的观感是"开机那会儿说话没反应，过一会儿又正常了"。

## 怎么复现（Windows，本机 2026-10-13 实测）

在 `main.splash` 的 `boot()` 里挂几个定时器，各自发一次 `model.speak`（宿主必然处理并打日志）：

```splash
start_timeout(0.5, || host.request("model.speak", {text: "边界测试四", voice: "zh-CN-XiaoyiNeural"} , fn(r){ ag_log.push({who: "tool" text: "0.5s 回执"}) }))
start_timeout(4.5, || host.request("model.speak", {text: "边界测试五", voice: "zh-CN-XiaoyiNeural"}, fn(r){ ag_log.push({who: "tool" text: "4.5s 回执"}) }))
start_timeout(5.5, || ... 5.5s ... ))
start_timeout(6.5, || ... 6.5s ... ))
```

观察宿主日志（`card-host.log`）里 `model voice: spoke ...` 行与卡片侧回执：

| 发出时刻 | 结果 |
| --- | --- |
| 0.2s / 0.35s / 0.5s | **吞**（无回执、无日志） |
| 1.0 ~ 3.0s（含从定时器链里补发） | **吞** |
| 4.5s / 5.5s | **通**（日志出现 `spoke 5 chars ... text=[边界测试四/五]`） |
| 6.5s | 时通时不通 |
| 12s 之后 | 稳定通 |

同一台机器、同一个二进制、同一条请求形状，**唯一的变量是发出时刻**。
从 `start_interval` 回调里发出的请求命中率更差（疑似与开机期的重入/调度窗口叠加）。

## 危害

1. **应用侧**：任何"启动即探测宿主能力"的写法（语音探测、设备探测、服务握手）
   会静默失败，只有在用户后续交互时重试才能恢复。做冷启动体验的产品一定踩。
2. **生态侧**：这正是"别的选手麦克风/语音一直在启动时试、一直不灵"的一类坑的一部分
   —— 能力并不缺，是**启动窗口的请求被吞**。调用方拿不到任何可诊断信息。
3. **可诊断性最差的一点**：静默。既没有 `[E]` 也没有超时回调，日志里完全无痕。

## 建议的修法（按侵入性排序）

1. **最稳**：请求投递层在启动窗口中把请求**排队**，等 isolate/宿主就绪后再发
   （或直接回一个「太早了，稍后重试」的错误回调 —— 至少不静默）；
2. 给每个 `host.request` 加**超时回执**：N 秒内无任何结果 → 回调一个
   `{"ok": false, "error": "no response"}`（现在无回执 = 永远无回执）；
3. 文档明示：**启动阶段不要做宿主往返**，或给出"宿主就绪"事件供应用等待。

## 本仓库的绕过方式（可复用）

- 语音探测按官方建议惰性化：「用时再探」＋探测期间积压用户请求（`vc_probe` / `vc_wait_say`）；
- 开屏配乐不依赖卡片侧请求：由启动器 `tools/launch.py` 用 `winsound` 直接放，
  并给卡片留一个 `voice-bridge.on` 字条；卡片侧仅在**有字条**时才做点播
  （哨兵文本 `[CG-BGM]` 走 edge 桥返回 PCM）；
- 卡片侧保留的宿主点播路径带 **ack 驱动重试**：没回执就隔 0.9 秒补发，
  收到回执就停（`cg_music_try`）。

## 回归测试该测什么

在 `boot()` 后 0.1 / 0.5 / 2 / 5 / 12 秒各发一次回显请求，断言 **每一个请求
要么有成功回执、要么有可诊断的错误回执**——不允许"两者都没有"。
