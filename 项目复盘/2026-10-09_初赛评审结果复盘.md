## 四、评审给的三条改进建议（我逐条做了技术核实）

### 建议 1（阻断级）：AI 通道用错了能力名

**评审原话**：全部 AI（三审、主编终审、常驻主编、语音）走 `llm.*`，而 `llm` 只服务系统应用，**商店应用调用会被宿主直接拒绝**——从商店安装后编辑部整体不可用。请迁移到 `model.complete`。

**核实结果：完全准确，而且比评审写的还多一处。**

| 核实项 | 结论 |
| --- | --- |
| 官方文档怎么说 | `docs/PUBLISHING.md` 第 163 行：`llm` 这个能力……"**只应答 `os.` 开头的系统应用（AI 提供商），所以商店应用用它一无所获**"。第 239 行再次确认：`llm` 和 `news` 只给 `os.` 系统应用 |
| 正确通道是什么 | 同一份文档第 168 行：改用 `model` 能力 → 调 `model.complete`。应用只声明"要快模型还是强模型"+ 一个数据结构，**宿主自己挑模型、自己管预算、密钥和应用完全隔离** |
| 我们的清单怎么写 | 真包 `manifest.json` 的 capabilities 里写的是 `"llm"` |
| 代码里有多少处 | **20 处** `llm.*` 调用。其中 `llm.chat`（就是干活的那些）**10 处** |
| 评审列了几处 | 9 处（1064、1998、2088、2262、2783、3002、3215、3333、3401） |
| **评审漏了哪处** | **3878 行——视觉主编写头版标语那处**。如果我们照着评审列的单子改，会把这一处漏掉，头版功能照样是死的 |

**这是本次最贵的一个坑，它最阴的地方在于：我们本地测试一切正常，完全看不出问题。**

---

**为什么本地跑得好好的？**

我们启动时会先问宿主一句"你这儿有没有模型可用"，答"有"就把 AI 开关打开：

```
fn make_plan(){
    host.request("llm.status", {}, fn(r){
        if r.is_ok && r.data.ready { ai_ready = 1 } else { ai_ready = 0 }
    })
}
```

这个探针问的是「**宿主有没有模型**」，而不是「**我这个小应用被允许用模型吗**」。本地开发环境的权限检查比正式商店宽松（文档明确写：官方那个 `card-host` 连 `model` 都不提供，得用完整的 OctoSense 壳），所以探针一路答"有"，三审、终审、常驻主编、语音、全部跑通——我们在 `PROGRESS.md` 里记的"主编 88.5 秒 / 5784 tokens，三视角编辑部 3/3 交回"，就是在这个宽松环境里跑出来的。

**换成评审的正式环境，同样的代码会被宿主一句话拒掉。我们的验证环境不等于评审的验证环境，这是本次最大的认知盲区。**

---

### 建议 2（交付事故）：仓库里躺着两个同名同版本的包

**评审原话**：仓库里另有一个同 id 同版本的模板壳 `my-entry/app/bundle`，容易让人拿错，建议删掉或改 id。

**核实结果：准确。**

| | 模板壳 `my-entry/app/bundle` | 真包 `my-entry/morning-brief/bundle` |
| --- | --- | --- |
| id | `morning-brief` | `morning-brief` |
| version | `0.1.0` | `0.1.0` |
| capabilities | `["storage"]` | `["storage","net","images","llm"]` |
| 完整性指纹 | `199bafb0…` | `77470aad…` |

**两个包的身份证号一模一样。** 评审用的是指纹比对才认出哪个是真包（评审原话："关卡通过、digest 一致"），纯靠肉眼看名字是分不出来的。这是好事——评审识别出来了；但这也是运气，换一个不做指纹核验的评审，可能直接拿模板壳去跑，那我们的真实功能一个都展示不出来。

### 建议 3（体验瑕疵）：语音失败时不给提示

**评审原话**：语音层失败时给一行状态提示，别静默返回。

**核实结果：方向对，但要补一个细节。**

- `vc_say_now()`（朗读）里第一行就是 `if !vc_tts { return }`——**无声退出，界面什么也不说** ✓
- 更明显的一处：真正调朗读服务的那个回调写成了**空函数** `fn(r){}`——意思是"我发了请求，但不管成功失败我都不看结果"。**失败彻底无痕** ✓
- 但要公平地说：探测语音能力那一步（`vc_probe`）其实是有文案的（"这台机器没有可用的语音能力，全程打字也算数"）。所以不是"全都没有提示"，是"**朗读这一步没有**"。

## 五、第三条"做得好的"要打个折：理解 ≠ 贡献

评审夸我们"对跨平台缺陷的理解与应对是全场最专业的提交者行为"。这句是真的，但它有个前提故事：

- 这个缺陷是 **`#75`**，**报告者是 `sansanyixyz331`（拾意 Pickup 那支队）**
- 修复它的补丁是 **`#79`**，作者**也是 `sansanyixyz331`**，**已合并进主干**（`78dfda5`）
- 我们做的是：**读懂了这个缺陷，并主动规避它**（选择按 Linux 的正斜杠算指纹，还自己把补丁挑过来验证了一遍）

**拾意那支队拿了 83 分，我们 72 分。**

差在哪，现在看得很清楚：**同样撞上别人的一个 bug，他们把它报上去并且修了（这是对生态的真实贡献，直接影响升级）；我们绕过去了，只保住了自己。**

这条要写进判据：**当你花时间绕过别人产品的一个 bug 时，先问一句"我把这个信息回流给上游了吗"。绕过去只保护自己，报上去才是贡献。** 而且这件事的成本极低——我们连复现步骤和验证脚本都已经有了，写一个 issue 而已。

（顺带说：报告缺陷和提交修复属于"生态贡献"，而官方在赛程里明说了**「技术进阶作品另核验贡献」**——这条线索意味着复赛阶段我们对生态的贡献是**能被算分的**，这是值得投入的方向。）

## 自测（先别看答案）

1. 如果只把 `manifest.json` 里的 `"llm"` 换成 `"model"`，但**不动**那 10 处 `llm.chat` 调用，你预测会坏在哪一层？为什么？
2. 我们的探针问的是"宿主有没有模型"。如果改成问"我这个小应用被允许用模型吗"，它能在**本地开发环境**里提前发现这次的问题吗？为什么？

---
## 答案

1. **坏在"接口与配置"层，而且比现在还糟。** 能力声明换成 `model` 之后，关卡会认为我们要用 `model` 通道；但代码里发的还是 `llm.chat` 请求——**我们被授予的权限和实际发出的请求对不上**。评审第 3 条标准（权限与主机最小且如实披露）会直接判"声明与实际不符"。**能力声明和调用代码必须成对改，只改一边比不改更差。**

2. **大概率发现不了。** 因为本地那个开发环境比正式商店宽松——它能答 `llm.status`、能跑通 `llm.chat`，就是因为它**根本没做这套权限检查**。探针问得再准，在一个不做检查的环境里也问不出"会被拒"。真正的提前发现信号不是"改探针"，而是**读文档读到"只给系统应用"那句话时就该警觉**——这类问题靠运行时探测是测不出来的，只能靠读规则。
